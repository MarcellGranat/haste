## ADDED Requirements

### Requirement: SMTP submission over STARTTLS
The iCloud connector SHALL submit mail to `smtp.mail.me.com` on port 587 using STARTTLS, with certificate verification enabled, before any credential is sent. It SHALL authenticate with the Apple ID address and the app-specific password read from the macOS Keychain service `com.haste.icloud`. The SMTP client SHALL issue only `EHLO`, `STARTTLS`, `AUTH`, `MAIL FROM`, `RCPT TO`, `DATA`, `RSET` (only on a refused message before `DATA`) and `QUIT`.

#### Scenario: Certificate not accepted
- **WHEN** the server certificate does not validate during the STARTTLS upgrade
- **THEN** the connection is closed before `AUTH`, no credential is sent, and the send is classified `NoEffect`

#### Scenario: Plaintext refused
- **WHEN** the server does not advertise STARTTLS
- **THEN** no credential is sent and the send is classified `NoEffect`

### Requirement: Single attempt and phase-aware outcome
The SMTP client SHALL expose each protocol phase (connect, TLS, auth, envelope, data) so that the send outcome can be classified exactly. It SHALL NOT retry any command, and SHALL treat a failure after the `354` response to `DATA` as `Ambiguous`.

#### Scenario: Refused envelope
- **WHEN** `RCPT TO` is rejected with a 5xx reply
- **THEN** the outcome is `NoEffect` and no message body is transmitted

#### Scenario: Failure after data
- **WHEN** the connection drops after the message body was written
- **THEN** the outcome is `Ambiguous`

### Requirement: Plain-text RFC 5322 message
The connector SHALL compose the message from the proposal's stored data only: `From` equal to the configured iCloud address, `To` the single resolved recipient, `Subject` as defined by the email-send spec, `In-Reply-To` and `References` from the thread when available, `Date` and a `Message-ID` generated by the connector. The body SHALL be `text/plain; charset=UTF-8` with dot-stuffing applied and CRLF line endings.

#### Scenario: Reply headers present
- **WHEN** the thread's last message has a Message-ID
- **THEN** the message carries `In-Reply-To` and `References` naming it

#### Scenario: Dot-stuffing
- **WHEN** a body line begins with a period
- **THEN** the transmitted line begins with two periods and the terminating `.` line is the only lone period

### Requirement: Sent copy by APPEND after acceptance
After the server accepts the message with `250`, the connector SHALL append a copy to the configured Sent folder (`sent_folder` in `icloud.json`, default `Sent Messages`) with flag `\Seen`, using a new IMAP session with the same Keychain password. This APPEND SHALL be the only mailbox write the connector makes, and it SHALL NOT occur outside the send path. If the APPEND fails, the proposal SHALL still be `sent` with result `sent:smtp;copy_failed` and SHALL NOT be retried.

#### Scenario: Copy appended
- **WHEN** the server accepts a send
- **THEN** one APPEND to the Sent folder is issued with the message bytes and `\Seen`

#### Scenario: Copy failure keeps the send
- **WHEN** the APPEND fails after the server accepted the message
- **THEN** the proposal is `sent`, the audit records `send.copy_failed` with no addresses, and no second submission occurs

#### Scenario: No copy before acceptance
- **WHEN** the server rejects the message before `250`
- **THEN** no APPEND is issued

### Requirement: Authentication failure during send is terminal
A rejected `AUTH` (535 or equivalent) during a send SHALL be classified `Checkpoint`, engage the kill switch, notify the human that the app-specific password must be renewed, and SHALL NOT be retried.

#### Scenario: Rejected AUTH
- **WHEN** the server rejects `AUTH` during a send
- **THEN** the send is refused without a `MAIL FROM`, the kill switch engages, and the human is notified

### Requirement: Tests use a local fake SMTP server only
The SMTP client SHALL be tested against a loopback fake SMTP server with a plaintext transport used only in tests, and against the existing fake IMAP server extended with `APPEND`. Tests SHALL assert the exact command sequence, that a failure at each phase produces the classification in the email-send spec, and that no test contacts a real server.

#### Scenario: Command sequence recorded
- **WHEN** a successful send test runs
- **THEN** the fake server records `EHLO`, `STARTTLS`, `EHLO`, `AUTH`, `MAIL FROM`, `RCPT TO`, `DATA` and `QUIT` in that order, with no repeats

#### Scenario: Failure at each phase
- **WHEN** the fake server fails at connect, STARTTLS, AUTH, RCPT TO, after DATA, and at APPEND
- **THEN** the outcomes are `NoEffect`, `NoEffect`, `NoEffect` with a Checkpoint, `NoEffect`, `Ambiguous`, and `sent` with copy_failed, respectively
